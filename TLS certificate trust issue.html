🔎 What’s likely happening

On VM1 (Oracle/OpenJDK + its cacerts)
→ The server’s SSL certificate chain is trusted

On VM2 (OpenJDK 11)
→ The JVM doesn’t trust the server certificate, so HTTPS calls fail

Typical error you might see:

javax.net.ssl.SSLHandshakeException:
PKIX path building failed

✅ Step-by-step fix

1. Compare the cacerts files

Check if they’re actually the same:

Bash
$JAVA_HOME/lib/security/cacerts

List contents:

Bash
keytool -list -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit

Do this on both VMs and compare.

2. Check the server certificate

From VM2:

Bash
openssl s_client -connect your.api.com:443 -showcerts

Look for:

  • Missing intermediate certs

  • Self-signed certs

  • Corporate proxy certificates (very common!)

3. Import the missing certificate into VM2

If VM1 trusts it but VM2 doesn’t, export from VM1 or fetch it:

Bash
openssl s_client -connect your.api.com:443 -showcerts > cert.pem

Then import:

Bash
keytool -importcert \
  -keystore $JAVA_HOME/lib/security/cacerts \
  -storepass changeit \
  -alias my-api-cert \
  -file cert.pem

4. Verify Java is using the expected cacerts

Sometimes Java uses a different truststore:

Bash
-Djavax.net.debug=ssl

Run your app and check logs for:

trustStore is: ...

5. Check for proxy differences (very common)

VM2 might be behind a proxy doing SSL inspection.

Check:

Bash
env | grep -i proxy

If so, you’ll need to import the proxy’s root cert.

6. Quick workaround (not recommended long-term)

You can bypass SSL validation temporarily (for testing), but don’t use in production.

⚠️ Common gotchas

  • Different Linux distros bundle different CA certs

  • OpenJDK builds (e.g. Debian vs RedHat) can differ

  • Corporate environments often inject custom root CAs

  • The server might not send full certificate chain

🧠 Best long-term fix

Instead of modifying JVM cacerts directly:

  • Create your own truststore:

Bash
keytool -importcert -keystore truststore.jks -file cert.pem

  • Run app with:

Bash
-Djavax.net.ssl.trustStore=truststore.jks
-Djavax.net.ssl.trustStorePassword=changeit

  • Descriptive enough so you recognize it later

Bash

-alias my-api-cert

👉 That’s completely arbitrary—you defined it.

Instead of random names like test or cert1, use something meaningful:

  • mycompany-proxy-root

  • partner-x-intermediate

Bash
keytool -printcert -sslserver your.api.com:443

You’ll see:

SHA256: AA:BB:CC:DD:...

Step 2 — Check inside cacerts

Run:

Bash
keytool -list -v -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit

👉 Look for the same SHA256 fingerprint

✔ Match → cert is already trusted
❌ No match → cert is missing

⚠️ Important nuance

Even if the server certificate itself is not in cacerts, it can still work if:

👉 The issuer (CA) is trusted

So check both:

  • Server cert ❌ (not required)

  • Issuer CA ✅ (required)

🧠 What you’re really checking

Java trust works like this:

Server cert → Intermediate CA → Root CA (must be in cacerts)

👉 You only need one trusted parent in the chain

🚨 Common mistake

People search for:

CN=*.hors-prod.caas.lcl.gca

But the real trusted cert is usually:

CN=CA Credit Agricole Server

  3. Search in cacerts:
